## Current architecture highlights

### UI/Frontend (as of 2026-07-17)
- **Dark theme** with token-based design: cool near-black background, ouro accent, jewel palette (indigo/violet/cyan/emerald/rose).
- **Persistent shell**: `AppShell` + `SidebarNav` (client, `usePathname`) on every authenticated page (tabs in `lib/auth/tabs.ts`). Since 2026-08-22 the sidebar is grouped in **sectors** (Analítico · Comercial · Operações, `sector` metadata on each tab) rendered as native `<details name="oraculo-setor">` — the browser handles the accordion, no React state; the active page's sector opens from `pathname`. Tabs without `sector` (Agenda, Parâmetros) stay loose; Admin keeps its own group. Sidebar badges come from a `badges` map (href → count) that `AppShell` assembles itself: the global alert count (`lib/alert-count.ts`, `unstable_cache` 60s) and the **per-user** Agenda count (`lib/agenda-count.ts`, `React.cache` only — a global `unstable_cache` key would leak counts across users).
- **Agenda (`/agenda`, 2026-08-10)**: first feature with per-user data. Server-rendered monthly calendar, task pop-up via `?editar=` (CSS-only overlay, backdrop is a close `<Link>` — first modal in the repo, still zero client JS), collaborative subtask checklist. User directory in `lib/users.ts` (auth admin API + 5-min cache; dev mock maps to a sentinel uuid). Tables use the repo's only **per-row RLS** (participant-only select via `security definer` helper); writes stay service-role in Server Actions with TypeScript authorization, and loaders always filter by user id explicitly (dev bypasses RLS).
- **Logística (`/logistica/etiqueta`, 2026-08-11)**: first feature that produces a **physical document**. Pallet labels at 100×150 mm printed straight from the browser (`@page { size: 100mm 150mm }`, no PDF library) with a server-rendered SVG QR Code pointing at `/logistica/palete/<code>`. Product and variations are **free text, deliberately unlinked from the product catalogue** (2026-08-13). The first version bound each variation to a real Olist SKU via `<datalist>` and died on the first real pallet: it printed `Kit pote 10 un 370ml azul 370 - 10 unid.` where `Pote de Vidro 370ml - 10 unid.` was wanted. Neither `nome` (marketplace ad title) nor `sku` is a physical product name — **the ERP's vocabulary belongs to the marketplace, not to the loading dock**. Check what text a catalogue actually holds before binding a new screen to it. The label text is frozen in the DB at print time: the label is a document, not a live view. See `docs/logistica-etiquetas.md`.
- **RPA Afiliados (`/rpa`, 2026-08-12)**: first feature handling **third-party personal data at scale** (CPF, birth date, address of 772 affiliates) and the first to **generate PDFs with a library**. Monthly Shopee affiliate report comes in as `.csv` upload (the AMS API still answers 403 to all four partner apps), retentions are computed per row and **frozen in the row** — a receipt is a document, not a live view. Its three tables are `service_role`-only **on purpose, against rule #8 below**: adding `grant select to authenticated` would expose the whole affiliate registry to any valid JWT. `pdf-lib` + `fflate` are a deliberate departure from the pallet-label "no PDF library" precedent — `window.print()` yields one N-page file, and accounting needs one receipt per person inside a ZIP. Money is integer cents rounded **per line** (rounding at the end cost 3 cents on July's INSS total). See `docs/rpa-afiliados-shopee.md`.
- **Reconciliação (`/reconciliacao`, 2026-08-25)**: pedido Shopee × NF Olist × líquido previsto × crédito efetivo da carteira, com pendências e previsão real da Shopee. O filtro usa a data do pedido; `Saldo após` é o saldo total da carteira depois do crédito, não o valor pago do pedido. O extrato financeiro é `service_role`-only e a tabela visual pagina 100 linhas; os cards vêm da RPC integral `shopee_reconciliation_summary`. A ingestão semanal é por loja e retomável, com cursores independentes para carteira e pendências em `shopee_reconciliation_sync_state`. Ver `docs/project-status-2026-08-25.md`.
- **`@oraculo/domain` is now a real dependency of the web app** (`allowJs` in the web tsconfig + `transpilePackages`). It used to be executable spec only, tested in parallel with the SQL; `/rpa` consumes it directly because two implementations of the same money calculation give two answers.
- **Metric cards**: shared `MetricCard` component (in `app/page.tsx`) with sparkline + variation chip, used across the app — not a one-off dashboard element. Delta color inverts for cost/taxes (rising is bad).
- **Sorted tables**: `/skus` has a dedicated client component (`useMemo` + `useState`); everywhere else uses the generic `app/components/sortable-table.tsx` (serializable cells: text/sort/href/badge/subtitle). Click headers to sort, click again to reverse, nulls always last.
  - Columns take an optional `hint`: renders a "?" mark + hover tooltip explaining the metric (pure CSS, `.sr-only` copy for screen readers). Hint texts are centralized in `apps/web/lib/column-hints.ts` so ML and Shopee explain the same metric with the same words — write new hints there, not inline.
- **SVG charts** (server-rendered, no client JS): tax composition donut, margin/ROI gauges, daily revenue area with dashed average line.
  - Single exception to "no client JS": the Importações map (`app/importacoes/leaflet-map.tsx`) is a Leaflet client component loaded via `next/dynamic` with `ssr: false` — Leaflet touches `window` on import.
- **Layout invariant**: `.workspace > * { min-width: 0 }`. Grid items default to `min-width: auto` and inflate to their content's intrinsic width, which made wide tables drag the whole page horizontally and push the sidebar off-screen. Wide content must scroll inside `.table-wrap`, never the document.
- **Visual identity**: `BrandMark` component (SVG inline, same source as favicon) — see `docs/brand-oraculo.md`.
- **Pricing calculator** (`/calculadora`): standalone rules, does not touch the fiscal engine. Marketplace presets are data, not logic — see `apps/web/app/calculadora/calculator.tsx`.

### Backend & data (as of 2026-07-17)
- **Three channels with their own ingestion** (all autonomous via pg_cron → Edge Functions; cadence and ownership in `docs/deployment-map.md`):
  - **Olist** — orders, stock, fiscal invoices; the primary revenue source.
  - **Mercado Livre** — `mercadolivre-sync` (`:55`) + notification inbox; sole owner of its rotating refresh token.
  - **Shopee** — 4 shops, each with its **own partner app** (sign with that shop's key; `invalid_access_token` is usually a wrong signature, not an expired token). `shopee-sync` is the **sole token renewer**; every other Shopee function only reads the token.
  - **Importações** — `importacoes-ais-sync` (6h) writes AIS vessel positions.
- **Channel analytics share one language**: sell-through speed over *days in stock*, rupture in R$/day, ABC 80/15/5, and a justified replenishment suggestion. Rules live in `docs/project-status-2026-07-17.md`.
- **Unit cost book**: view `oraculo_sku_unit_cost` (migration `20260716240000`) resolves cost per marketplace SKU — manual override > `olist_products` (ignoring R$ 0, which most ERP SKUs have) > kit effective cost. ML and Shopee both read it; don't re-implement cost resolution per page.
- **Fiscal snapshots** (hourly via pg_cron, `**:15`, 14-day retention — migration `20260710190000`): `fiscal_margin_summary`, `fiscal_sku_margin`, `fiscal_channel_metrics`.
  - Current-month window (default) reads snapshots (instant); a custom date window computes live via RPC with try/catch degradation — never silently shows the wrong month.
  - Snapshot **history** (not just latest) is readable by `authenticated` (migration `20260712100000`) to power card sparklines.
  - All queries tested under `authenticated` role with 8s timeout; none exceed.
- **RLS + auth**: business-data reads via authenticated client (anon key + user JWT); service-role reserved for writes/admin.
- Fiscal layer: Financeiro rules (Jacarta profile, Lucro Real + RET), kit cost expansion by component, per-SKU margin/ROI with tax decomposition.
- **Traps that already cost real bugs**:
  - **PostgREST caps at 1.000 rows** — channel pages paginate with `fetchAllPages`.
  - **Aggregates never come from the sync's own window** — they are recomputed from the `*_sales_daily` series by RPC; a 2-day cron window once distorted the rupture numbers.
  - **Never count orders from `olist_order_items`** — item coverage swings by day (26% on 21/07, 100% on 26/07) because the orders importer keeps backfilling past days ahead of the items backfill. Counting there undershoots volume ~3x. Units come from items (always a floor); order counts come from `olist_orders`. Full measurement in `docs/olist-item-coverage-2026-07-28.md`.
  - **Reading `olist_orders.payload` is the cost driver** — 329k rows / 957 MB; the channel name only exists inside the jsonb, so grouping by channel over thousands of orders detoasts it (5,0s vs 1,4s without). Heavy aggregation goes to a daily cache + `pg_cron`, never live. A `stored` generated column is not the answer — it rewrites 957 MB under `ACCESS EXCLUSIVE` and blocks the sync.
  - **Off-marketplace orders distort quantity rankings** — a single B2B order entered straight into the ERP (empty `payload.ecommerce.nome`) carried 213.960 units, more than every marketplace combined. Quantity rankings filter to orders that have a channel; the off-market volume stays in the cache and is disclosed separately. **They distort `/skus` margin too** — that calculation does *not* separate channel, so a B2B sale drags the SKU's average unit price down and reports a margin that never happened (cabide `213997`: −131%).
  - **A cache with no cron is a silent, invisible failure** — `oraculo_sku_current_unified_cache` froze on 2026-06-19 and stayed wrong for 45 days because `refresh_oraculo_unified_sku_cache()` existed but nothing scheduled it (`oraculo-olist-derived-hourly` skips it by design). Nothing errored; the pages just kept serving June. Rupture alerts said 5 SKUs when there were 170. **When adding a cache table, schedule it in the same migration, and add its `refreshed_at` to `/status`.**
  - **`refresh_oraculo_unified_sku_cache()` runs ~5 min and cannot go through the API** — `supabase db query` hits the 2-minute statement timeout, and since both inserts share one transaction the whole thing rolls back. Run it via `pg_cron` with `set local statement_timeout`.
  - **Never re-implement cost resolution** — `oraculo_sku_margin_30d` did it in a local `olist_costs` CTE instead of using `oraculo_sku_unit_cost`, and inherited two defects the canonical view already solves: it hardcodes `'olist'::text AS source` (so every `source='shopee'` SKU fails the join — R$ 7,64 mi of revenue) and filters `tipo IS DISTINCT FROM 'K'` (so kits get no cost — R$ 3,61 mi), plus `COALESCE(preco_custo_medio, preco_custo)` returns `0` instead of falling back, because the ERP stores `0`, not `NULL`. Combined effect: 80% of revenue reported as "sem custo" when only R$ 15k genuinely lacks cost.
  - **`oraculo_fiscal_channel_sales` returns no Shopee rows at all** — it reports R$ 5,09 mi over 180 days while `oraculo_fiscal_invoices_valid` grouped by `channel_label` reports R$ 14,6 mi with Shopee at ~70%. Any channel-mix read must go through `oraculo_fiscal_invoices_valid`.
  - **`source='olist'` and `source='shopee'` are the same sale twice** — Olist issues the NF for every channel, Shopee's direct API repeats it under a different SKU naming (`214013` vs `CABIDE VELUDO-50UN-PRETO`, only 5 of 501 SKUs match by text). Summing both double-counts: R$ 12,7 mi against R$ 8,27 mi of real billed NF over 30 days.
  - **Returns: the return NF filter is `fiscal_origin_type='devolucao'`, never `fiscal_invoice_type='E'`** — the type also drags in purchases and imports. July/2026: origin gives 4.074 NFs / R$ 296 mil; type gives R$ 5,58 mi. 18x inflation. The return NF has `order_id`/`order_number` **zeroed** and an empty `ecommerce` block, so there is no direct key back to the order: the join goes return → **sale NF** via `ecommerce.numeroPedidoEcommerce` (exact) → return NF via CPF + SKU + 90 days (heuristic, carries a `match_score`).
  - **A marketplace SKU rarely matches the Olist NF SKU** — 21 of 108 TikTok SKUs (19%), same naming trap already documented for Shopee. Never translate the SKU: take it from the **sale NF already matched by order number** (97,6% of them have a single SKU).
  - **Compare money against `olist_invoices.total_amount`, not `olist_invoice_items.total_value`** — the item line carries the product's list price. Using it produced a median ratio of exactly 2,003 and 327 false "divergence" flags where there were 25.
  - **Shopee caps `create_time` windows at 15 days** — asking for 16 returns `error_param` and the window comes back EMPTY **without failing the run**. Chunk into 14 days. And **never run the 4 shops in one invocation**: it exceeds the edge function wall clock and dies with no log (`shopee-sync-products` and `shopee-returns-sync` are both scheduled per shop for this reason).
  - **Shopee financial pagination cannot run in one Edge invocation** — `payment.get_income_detail` ignores `date_from/date_to` for pending income and takes ~6–7 s per 100 rows; August measured 10.829 pending rows in one shop. Wallet volume reached 28.593 credits in 25 days. Persist both cursors and process bounded pages per invocation; a long loop hits the 150 s idle timeout. Pending `estimated_payout_time=0` means “Aguardando conclusão”, never invent a date.
  - **The ML `/claims/search` ignores date filters and sorting** — `date_created_from`, `date_created_to` and `sort` return HTTP 200 and do nothing; only `offset` works, and at least one filter (`stage`/`type`) is mandatory. Page backwards and filter on our side.
  - **Day-coverage inferred from data presence stalls on an empty day** — a refresh loop that asks "does this day have rows?" never marks a day with no source rows, so it re-picks it forever. Track processed days in a control table (`oraculo_olist_order_ref_cache_days`); a day with zero rows is a processed day.
  - **A shared runs table needs a source marker, or `/status` lies** — `mercadolivre_sync_runs` has no `source` column and is written by two functions; `shopee_sync_runs` has one but is multi-source. The returns routines tag `meta->>'source'` / prefix `source`, and `/status` filters on it. Without that the screen shows a healthy run belonging to a different routine — the worst kind of green light.
  - **"Refreshed in the last N hours" is the wrong staleness rule for the current day** — the sale-NF cache used 20h for every day. Correct for a closed day, wrong for today, which keeps receiving invoices: anything issued after the cron pass stayed out until tomorrow, and a return against it produced a false `sem_nf_venda`. Hot window (3 most recent days) refreshes hourly; closed days stay immutable.
  - **An estimated value must never wear the clothes of a measured one** — the ML reports no refund amount, so the value falls back to the sale NF (`refund_amount_effective`), but `refund_amount` is never overwritten and `refund_amount_source` travels with it to the screen. It is the ORDER total, not the refund: a partial return overstates.
  - **Enum semantics must be confirmed against the data, never assumed** — Shopee's `return_solution` was mapped inverted (0 is RETURN_REFUND, not REFUND_ONLY). The tell was in the payload all along: every `solution=0` row carries `needs_logistics=true`. The failure was silent and expensive — returns WITH goods coming back were filed as `refund_only`, which by definition needs no return NF, so the fiscal cross-check never asked for one. Shopee showed 4 "NF confere" against 658; only comparing channels side by side exposed it (TikTok: 253 of 554).
  - **`drop view ... ; create view ...` apaga todos os `COMMENT ON` da view e das colunas dela** — `create or replace view` preserva (mesmo oid). O repo derruba e recria views em pelo menos 4 migrations. Desde 21/08 as descrições do banco são a fonte da aba `/documentacao` e aparecem dentro do Metabase, então uma view recriada sem reaplicar seus comentários silenciosamente desdocumenta o banco nos dois lugares. Toda migration que derrubar uma view precisa reaplicar os `COMMENT ON` no mesmo arquivo; a barra de cobertura em `/documentacao` é o detector.
  - **Um campo que existe no payload não é um campo preenchido** — `olist_orders.transportador.nome` foi materializado em coluna na Fase 1 da Logística a partir do shape do jsonb e veio **0% preenchido** em 138.873 pedidos: quem despacha é o marketplace, então o ERP não tem transportadora para gravar. `codigoRastreamento` idem, ~1% (só Mercado Envios). Meça a taxa de preenchimento **antes** de materializar, e grave a cobertura medida no `COMMENT ON` da coluna — senão o próximo a ler o dicionário repete o erro. Consequência de projeto: o Olist não serve como fonte de expedição multicanal.
  - **A funnel that does not add up is a lying funnel** — the returns funnel dropped 16% of the top until the `cancelada` stage was added. Every stage that partitions must sum to the top, and stages that are a *subset* of another must be visually marked as such.

## Making changes

1. **CSS**: dark theme tokens live in `apps/web/app/globals.css` (`:root`). Edit token values, not hardcoded colors.
2. **Fiscal logic**: pure functions in `packages/domain/fiscal.js`, tested in `fiscal.test.js`. Run `pnpm test` to verify. Never let the standalone calculadora (`/calculadora`) read from or write to this layer — it's intentionally independent.
3. **Database**: add migrations in `supabase/migrations/`, apply via `npx supabase db query --linked --file <migration>` (never use `db push`).
4. **Tables**: prefer `app/components/sortable-table.tsx` (generic, serializable cells) for new sortable tables; `/skus` keeps its dedicated component for historical reasons. Explain calculated columns with `hint`, and put the text in `lib/column-hints.ts`.
5. **Charts**: SVG components in `apps/web/app/components/`, server-rendered (no hydration).
6. **New pages**: wrap with `<AppShell alertCount={await loadActionableAlertCount()}>` so the sidebar and badge stay consistent.
7. **Returns**: three sources write into the canonical `oraculo_returns` (Shopee/ML by API, TikTok by .xlsx upload on `/devolucoes`); the UI reads only from the canonical layer. `Refund rejected` is NOT a loss (37% of TikTok rows) and `refund_only` never produces a return NF — `oraculo_return_counts_as_loss()` and `return_type` exist to keep both out of the totals and out of the "missing NF" flag. Reason maps are DATA (`oraculo_return_reason_map`), not code.
8. **New table read by a page**: `grant select ... to authenticated` **and** a `for select to authenticated` policy. Without both, the page degrades quietly (the Shopee shop name silently rendered as a raw id — migration `20260716250000`) instead of failing loudly. **Exception, when the table holds third parties' personal data** (`oraculo_rpa_*`, `shopee_order_escrow`): keep it `service_role`-only, read it from the page with `createSupabaseAdminClient()` after `requireTabAccess(...)`, and say why in the migration header — otherwise someone will "fix" the missing grant.
9. **Exports**: an export route must reuse the page's `build-suggestions.ts`, never recompute. The spreadsheet is the screen by construction — that's the whole point of the shared builder. Sheet helper: `lib/xlsx.ts`.
10. **New Shopee function**: read the token, never renew it (renewal is exclusive to `shopee-sync`), and sign with the shop's own partner app key.
11. **Documentação do banco**: tabela, view ou função nova nasce com `COMMENT ON` na mesma migration que a cria, e objeto renomeado leva o comentário junto. As descrições vivem no catálogo do Postgres (não em markdown) porque assim aparecem na aba `/documentacao`, dentro do Metabase (Table Metadata) e no DBeaver — ver `docs/project-status-2026-08-21.md`. Cobertura atual e o que falta: `/documentacao/dicionario?pendentes=1`. Nunca edite uma migration de comentário já aplicada; corrija em migration nova (`COMMENT ON` é idempotente, a última vence).
12. **Status**: after significant changes, update `docs/project-status-YYYY-MM-DD.md` and add an entry to `CHANGELOG.md`. Point `README.md`'s "First files to read" and "Current production state" at the new status doc. This is the rule most often skipped — two shipped changes (the 15-item cap and the map popup) had to be back-documented on 2026-07-17 because it was.
